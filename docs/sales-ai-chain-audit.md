# 销售通话 → 跟进 → 企业知识 → AI 辅助链路检查

检查日期：2026-10-23。范围：当前仓库前后端、数据库迁移及已有验证说明；本次为静态代码检查，未连接电话平台、未调用真实 AI、未访问业务数据库，未重新执行历史测试。历史部署说明不能作为当前运行配置的证明。

## 结论

目标业务链路合理，但当前仅完成部分基础功能，尚未形成闭环。已经具备手工登记通话、上传播放录音、调用 AI 转写总结、人工编辑保存总结、客户跟进时间线及共享文章知识库。真实外呼、自动录音、AI 总结写入跟进、案例沉淀与 RAG 销售辅助均未打通。

| 环节 | 代码现状 | 缺口 |
| --- | --- | --- |
| 外呼 | 前端 POST /api/calls；后端保存客户、状态、时长、备注 | 没有向电话服务商发起拨号，没有平台回调与真实通话状态同步 |
| 通话录音 | 上传、鉴权播放，音频保存在 MySQL | 没有电话平台录音采集与自动导入 |
| AI 分析 | 两步调用：转写、纯文本总结；异步执行，可重试 | 服务商真实效果未在本次验证；无结构化业务字段、说话人及时间戳定位 |
| 人工确认 | 单独保存 reviewedSummary、确认账号和时间 | 确认不会更新通话备注，也不会新增跟进记录 |
| 客户跟进 | 汇总任务、通话备注、消息、系统事件 | 时间线读取 CallRecord.note，未读取录音确认总结 |
| 企业知识 | 管理员维护文章，员工阅读，标题/正文关键词搜索 | 无案例导入、分块、向量索引、召回、答案生成与引用链路 |
| 销售 AI 助手 | 本次检查未找到对应实现 | 缺少按客户上下文及知识检索生成建议、采纳反馈和业务效果闭环 |

## 已定位的业务问题

1. **通话登记不能代表真实呼叫。** CallService.create 直接接受人工填写的状态和时长，保存后更新客户 lastContactAt。如果登记未接通也更新，业务上应明确它代表“最近尝试联系”还是“最近有效沟通”，避免后续 AI 和报表混用。
2. **录音确认结果与跟进脱节。** RecordingReviewController.save 只更新录音表；CustomerFollowUpService.callRecord 只读取通话 note。销售已核对的内容不会自动出现在客户跟进时间线。
3. **当前总结不能直接承担可靠的业务级联。** RecordingAiClient.Result 只有 transcript 和 summary。需要从纯文本中可靠地区分事实、建议、明确约定、待确认事项，才能生成跟进和待办。
4. **共享文章不具备客户级隔离。** KnowledgeController 的文章读取没有客户归属过滤。现有设计适合共享资料；直接复制客户录音和跟进到这里会扩大可见范围。客户私有材料与企业共享案例应使用不同的访问范围。
5. **当前质检页面的完成标记不等于录音人工确认。** app.js 的质检视图使用独立的 /call-reviews 后端状态，同时有本地缓存；录音确认使用录音表 reviewedAt。CallReviewService.update 没有要求录音分析完成或总结已确认，因此可出现“已完成质检”但录音总结未核对的情况。应明确这两个动作的关系，统一质检指标口径。
6. **分析可靠性仍是本地任务模式。** 当前为进程内两个工作线程、无等待队列；过期任务需手动重试。若后续依赖自动跟进、案例和索引，应引入持久化任务与可恢复的逐步状态。
7. **外部处理确认目前只在前端校验。** recordings.js 检查勾选项，但分析 POST 接口没有接收、校验或记录此次授权信息。若业务依赖逐次确认，应在服务端记录授权主体、时间和录音版本。

## 建议的目标闭环

外呼请求 → 平台通话 ID → 状态回调 → 录音归档 → 转写 → 结构化分析 → 跟进草稿 → 销售确认 → 正式跟进 → 案例提炼/脱敏审核 → 企业知识索引 → AI 检索引用 → 销售采纳及业务结果反馈。

支持两种跟进方式，共用同一来源和确认流程：

- 级联生成：分析完成后自动生成跟进草稿，销售核对后保存为正式记录；明确约定可生成待办草稿，建议不直接当成已约定事项。
- 主动辅助：销售在客户详情中选择有权限的通话，请 AI 根据通话内容起草或改写跟进，展示原话依据，再确认保存。

“生成跟进”“创建待办”“共享案例”分别记录状态。客户跟进保存成功不应因向量索引临时失败而回滚；索引失败可独立补偿重试。

## 数据与知识设计

- **来源材料**：企业/访问范围、客户 ID、通话 ID、录音版本、文件摘要、转写版本、分析批次、模型及提示版本。原始事实、AI 草稿、人工修订分别保留。
- **分析结果**：客户需求、问题异议、销售回应、明确承诺、下一步、约定时间、待确认项；每条事实附原文片段，支持时间戳时补充定位。未提及保持空值或标注未知。
- **正式跟进**：来源通话和分析版本、草稿/已确认状态、正文、确认人及时间。以来源及生成用途建立幂等约束，重复点击和任务重试不得重复新增。再次分析不得静默覆盖已确认记录。
- **案例知识**：业务场景、客户阶段、异议、应对策略、结果及结果观察时间、适用条件、审核状态、来源版本和可见范围。失败案例同样可沉淀；没有成交证据不能标为成功案例。
- **检索索引**：知识版本、分块 ID、向量模型版本、访问范围、来源引用和有效状态。更新、删除、客户转移及撤回共享时，同步使相关索引与缓存失效。

原始录音、转写、分析、跟进都作为可追溯的知识来源；客户私有材料在授权范围内检索。企业范围复用的是经过脱敏审核的案例和经验，避免把所有客户原文直接开放给全员。若后续支持多企业部署，还需补充企业隔离；不能把“企业知识库”的命名当作已经实现租户隔离。

RAG 的作用是检索资料并据此生成答案，不代表模型会自动训练或永久学会企业业务。回答需展示引用、区分事实与建议，缺乏依据时说明不足；检索前及读取来源时都校验权限，不能先取出全量材料再交给模型过滤。客户对话里的指令按资料处理，不能触发系统操作。

## 实施顺序与验收

1. **先补跟进闭环**：录音确认界面增加“保存为跟进”，与独立的“保存总结”明确区分；客户时间线可见并能回溯录音。验证越权、重复提交、录音替换、再次分析和并发编辑。此阶段可沿用现有录音上传，不依赖电话平台。
2. **再补案例沉淀**：从已确认内容生成案例草稿，补充脱敏、审核、来源及撤回机制；客户私有材料和共享案例的访问测试均通过。
3. **接入 RAG 助手**：完成分块、索引、权限过滤、召回、引用回答；用真实业务题集验证命中率、引用正确性、越权拒绝与无依据时的回答，采集销售是否采纳及原因。
4. **接通真实电话与自动化**：选定电话平台后实现拨号、回调验签、事件去重、乱序处理、客户关联、录音安全下载及补偿；AI 服务配置后用授权录音验证真实质量。人工上传继续作为兜底入口。
5. **衡量业务效果**：跟进填写耗时、确认后修改比例、约定事项遗漏率、知识引用/采纳率、客户推进及成交结果。结合业务阶段和样本比较，避免仅凭通话时长评价销售能力。

完整验收样例：一通真实授权电话结束后录音自动关联正确客户；AI 输出有原话依据的草稿；销售修订确认后时间线出现且不重复；案例审核后被相关业务问题检索命中并展示来源；无权限员工不能查看客户原文；源资料撤回后不可再召回；失败任务可重试且不重复写入。
