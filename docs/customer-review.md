# 婚恋客户复盘与成交案例

入口为客户详情「AI客户复盘」。原有逐通话的跟进草稿、提醒和来源选择保持独立。

每次新转写、单通分析更新、确认跟进或客户阶段变动后，服务端在下一轮扫描识别输入变化，自动生成一个客户累计复盘版本。相同资料不会重复生成；完成的历史版本不覆盖。既往已授权AI处理的录音也参与初始化复盘，不批量新增历史跟进提醒。

累计复盘包含客户需求与当前阻碍、沟通优点、销售改进、下次沟通建议、前后变化。DeepSeek直接分析该客户的历次通话原文和已确认跟进，结合既往建议；既往AI判断不作为客户原话。每条引用在服务端逐字核验并保留来源通话/跟进、时间、销售和时长。只有不同通话的前后证据才允许标记观察到变化，其他标待验证。原录音不是婚恋场景时明确场景不符，不能强套婚恋信息。

系统中客户状态「已成交」表示婚恋服务签约，不表示婚配成功。状态更新会生成新复盘，DeepSeek在成交版本内起草案例；用户核对、修改并勾选事实及脱敏确认后才发布到知识库「婚恋成交复盘」分类。公开文章仅包含确认后的标题正文，多次原始通话的来源关系保留在服务端，其他员工无法查看原始录音/转写/私有复盘。发布记录保存操作者，按客户唯一防重；未成交、过期版本、缺少确认和明显身份信息均阻止发布。管理员可按知识库现有权限维护已发布案例。

后台复盘使用独立单线程执行器，不阻塞通话提醒扫描；任务和版本持久化MySQL，10分钟租约允许服务重启恢复，最多自动尝试3次，失败可手动重试。失败不影响手动跟进。模型沿用已配置的DeepSeek；RAG知识问答及公司案例检索继续通过原有入口使用。

当前单份累计复盘最多100通、输入120000字符。超过时明确提示需分阶段整理，不静默截断，不生成不完整的成功案例。本次不包含任意长度档案的分层压缩。未授权AI处理的来源阻止累计处理，需先完成授权。

API（均需要当前客户归属人或管理员，no-store）：

- GET `/api/customers/{no}/review`：最新任务、最近完成版、最近20版历史及是否有新资料。
- POST 同路径：请求更新或重试失败的同一资料版本。
- GET `/api/customers/{no}/review/{id}`：指定历史版本。
- POST `/api/customers/{no}/review/{id}/publish`：version、title、content、sharingConfirmed=true；事务内检查成交、资料版本和权限，保存共享文章与多通话来源。

配置：`recording.review.enabled`（默认跟随录音队列开关）、`recording.review.initial-ms`（45000）、`recording.review.scan-ms`（30000）。数据库迁移V46，仅新增客户复盘表，不改写原有录音、转写、跟进或公司案例。
