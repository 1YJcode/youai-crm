# 通话列表压测（2026-10-23）

测试对象为本次客户归属状态功能完成后的 `/api/calls`，没有修改业务服务或业务数据库，也没有上传录音、调用外部 AI。使用专门创建且执行后删除的 MySQL 8.4 容器，以及启动于随机本地端口的 Spring Boot 实例。

通过真实 HTTP 请求及销售账号 JWT 运行，包括鉴权、数据库访问及 JSON 返回。连接池上限 10；使用 Hibernate 统计 SQL prepare 次数。SQL 数量包含鉴权，不等同于 MySQL 物理磁盘读次数。统计开销、本机资源共享及网络环境都会影响耗时。

构造两档合成数据：1,000 客户/10,000 通话，以及 10,000 客户/100,000 通话，数据库另外包含初始化演示记录。每客户 10 条通话，混合本人负责、本人已转出和无权查看的他人记录。每页 20/100 条，并发请求数 1/10/30；每档每场景预热后持续发起请求 5 秒并等待在途请求完成。测第 0/5 页，单次 SQL 探针测第 0 页。并发指同时在途请求，不代表相同数量的在线用户。

这是本机短时、热缓存、闭环压测，不是生产容量认证、极限吞吐或长期稳定性测试；没有测试深分页、每条通话都来自不同客户、上传下载音频或 AI。没有运行修改前的对照实现，因此结果能确认当前查询放大，不能量化新增功能相对旧版的性能差值。

可复现测试：`backend/src/test/java/com/youai/crm/communication/CallListLoadTest.java`。测试默认跳过；显式设置进程环境变量 `RUN_CALL_LOAD=true` 后使用 `scripts/test-recording-mysql.ps1 -TestClasses CallListLoadTest` 运行。测试还校验数据库必须为运行脚本创建的本机 recording_test 数据库。原始逐场景结果位于 `.tmp_call_load_results.json`；运行与迁移证据保存在脚本输出的 `.tmp_recording_mysql_*/`。

## 结论与处理建议

当前实现存在数据库查询放大，不能断言不会明显增加压力。每页 20 条一次请求执行约 47–49 条 SQL，每页 100 条约 223–225 条。30 并发下，十万条通话的每页 100 条场景 P95 约 2.04 秒，吞吐约 18.4 请求/秒；在本次样本中继续增大并发已不能明显增加吞吐。

列表的 `CallService.response` 对每条通话查询客户，再由权限检查再次查询客户；客户实体还关联完整资料及集合。这里的合成客户没有头像大字段、丰富标签等真实资料，因此真实环境负担可能更高。总数据量增长也会影响列表排序、总数及权限筛选；本次没有拆分每条 SQL 的执行耗时，不能把全部延迟归因于状态计算，也不能据此量化相对旧版的增量。

建议上线前批量读取本页客户编号对应的负责人 ID 投影，统一计算状态及访问权限，避免逐条读取完整客户；然后使用相同数据与场景做前后对照。必要时继续检查带权限筛选和排序的执行计划。本次仅压测，没有修改业务实现或部署业务服务。
