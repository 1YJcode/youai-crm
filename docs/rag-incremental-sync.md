# RAG 增量同步与轻量查询

## 运行方式

业务数据库保持唯一权威来源。独立后台线程启动约5秒后执行首次对账，之后默认每15秒尝试启动一轮；上一轮未结束不会重叠执行，也不占用其他业务定时任务的线程。

后台以100条为一页按ID游标读取公司可共享知识和通话来源。通话正文、AI摘要、销售确认跟进使用与问答完全相同的渲染器和版本指纹。先检查远端目录中的删除/取消共享，再仅上传版本变化的资料；未变化的正文不通过内部网络传输。更新只写入该资料的分块，不重建公司或客户的整套向量索引。

采用周期对账而非事件队列：业务数据和持久化检索目录提供可恢复状态。服务失败、重启或单条失败后，下一轮继续发现差异并重试，不依赖用户提问。每条操作失败不阻断其他资料，管理员可查看 `GET /api/knowledge/rag-sync-status` 的状态、完成时间、更新/删除/失败数。`RETRY_PENDING` 表示后续自动重试。

## 协议

所有内部接口要求 `X-Rag-Token`，不开放给浏览器。

- `GET /v2/catalog`：返回范围、资料编号、版本、索引令牌，不返回正文。
- `POST /v2/sync`：提交单条变化的正文，或 `document:null` 删除；`expected` 必须等于当前令牌，否则409，下一轮重新读取目录。新版本写入完成后才原子发布到SQLite目录。
- `POST /v2/search`：只接受问题、授权范围、资料编号/版本和结果数量；资料引用中传正文会返回422。没有同步到对应版本的资料不参与检索。
- `POST /v2/cleanup`：主动清理孤立版本、无读者的旧版本、对应嵌入缓存及旧V1存储。

业务后端仍然在检索后、返回回答前检查权限和版本。删除和撤权立即在业务端禁止使用；检索副本在后台下一轮清理，实际延迟取决于当前一轮工作量和服务可用性，不保证15秒内完成。正在执行的检索持有版本引用，清理会等这些检索结束再处理。

## 缓存和并发

BM25按授权资料版本组合缓存，最多32组，查询不重新构建未变化的组合。首次访问新的组合仍需构建一次。普通检索执行不持有同步写锁；同步准备期间旧版本可供在途请求读取。云端嵌入网络调用不再持有整个缓存数据库的锁。

当前部署使用单个检索进程（Docker明确指定 `--workers 1`），它可以处理多个并发请求。版本引用计数在进程内，因此不要对同一数据目录启动多个检索进程。若需要多实例，应先实现跨进程版本租约或独立检索存储。

## 升级与恢复

同时发布本次后端和检索服务。首次后台扫描自动建立V2索引；此期间问答可能提示资料正在同步。业务数据库无需新增迁移。

V1查询默认410，避免旧协议继续写入全量快照。后台完成扫描后的清理请求会删除旧V1集合中的数据和旧标记文件。`RAG_LEGACY_ENABLED=true`仅用于旧协议测试/临时迁移，并会暂停旧存储清理；正式部署不要开启。

保留 `/data/rag` 持久化卷，其中 `catalog.sqlite` 保存已发布版本。索引可从业务数据重建；若手工清空索引，需同时重建目录，不能仅删除Chroma而保留目录。单条写入中断产生的孤立分块会由后台清理。

配置：`RAG_INDEX_SYNC_ENABLED`（默认true）、`RAG_INDEX_SYNC_POLL_MS`（默认15000）、`RAG_INDEX_SYNC_INITIAL_MS`（默认5000）。后台同步仍以 `RAG_NOTEBOOK_ENABLED` 和内部令牌已配置为前提。仅需要暂停同步时可以关闭前者，查询继续使用已有索引。

清理调用存储引擎的删除接口，并清除应用缓存；这不等同于对磁盘页、数据库日志或外部备份进行取证级擦除，备份保留与存储压缩需按运维策略执行。

## 验证

Python回归覆盖增量写入、仅引用查询、范围隔离、失败重试、目录恢复、过期写入拒绝、无查询删除清理、旧存储清理，以及30个受控并行请求期间的版本保护。Java回归覆盖后台对账、未变资料零上传、失败重试、传输协议以及原有权限/撤权/引用校验。

受控并发测试不代表真实模型吞吐量测试。正式承诺10/30人同时问答的等待时间前，还应使用实际资料和模型额度执行压测。后台目前仍分页读取业务资料计算版本；更大规模时可进一步增加事务内变更记录，减少周期扫描成本。
